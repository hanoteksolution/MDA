# Tenant Provisioning Architecture

## Target orchestration

Create one `TenantProvisioningService` that composes, rather than replaces, existing services:

```text
RegistrationRequest
  → validate catalogs, agreements, email and idempotency
  → reserve normalized slug/domain
  → atomic database provisioning
      → PlatformService.create_shop foundation
      → BusinessPresetService / sync_tenant_modules
      → existing subscription/trial services
      → ChartService.ensure_default_chart
      → audit events
  → transaction commit
  → asynchronous welcome/optional seed side effects
  → READY
```

`PlatformService.create_shop()` should be decomposed into explicit idempotent stages over time, but remain the compatibility foundation initially. `DemoTenantService` should call the same orchestrator with mode `DEMO`, followed by existing seeders. Platform-created shops use mode `INTERNAL`; public registrations use `TRIAL` or `PRODUCTION`.

## Lifecycle

Recommended registration/provisioning states:

`PENDING_EMAIL → VERIFIED → VALIDATING → PROVISIONING → CONFIGURING → READY`, with `FAILED_RETRYABLE`, `FAILED_FINAL` and `CANCELLED` terminal/control states.

Tenant state remains the business-access lifecycle. Add `pending` and `archived` only if product policy requires them; do not overload provisioning state onto `Tenant.status`.

## Transaction and side effects

All database-bound foundation stages run in one outer `transaction.atomic()` block. Slug/domain conflicts are resolved by database uniqueness and mapped to a 409 response. Use `transaction.on_commit()` for email, metrics and optional Celery work. Critical database initialization must either complete or roll back; non-critical email failure must not corrupt a ready tenant.

If expensive module demo seeds are asynchronous, the tenant remains non-ready until required jobs complete. Jobs must be stage-idempotent and safe to retry.

## Idempotency

Accept an opaque `Idempotency-Key` generated by the client. Persist a hashed/canonical key plus payload fingerprint on `RegistrationRequest`, with a unique constraint. Same key/same payload returns the existing result; same key/different payload returns conflict. Never use password re-submission as the idempotency credential.

Do not persist plaintext passwords. Preferred verified-email flow creates the user inside the atomic provisioning transaction after verification while holding only a short-lived server-side registration secret/token design that cannot reveal the password. A simpler alternative is to create an inactive Django user with a hashed password during pending registration, then activate/provision after email verification.

## Required database additions

- `RegistrationRequest`: safe public ID, status, normalized payload excluding password, payload fingerprint, idempotency hash, email, timestamps, failure category and retry count.
- `EmailVerification`: hashed single-use token, expiry, consumed timestamp and attempt counters, or reuse a proven existing verification package.
- `AgreementAcceptance`: registration/tenant/user, document type, policy version, accepted timestamp and safe request metadata.
- `ProvisioningJob`: registration, tenant, mode, stage, status, attempts, error category, safe error summary, started/completed timestamps.
- Optional `SubdomainReservation` only if email verification defers provisioning long enough to require a lease; otherwise database creation within the atomic transaction is sufficient.
- Extend `TenantDomain` with explicit status only if custom-domain verification is introduced; its existing unique `domain` field already protects canonical host collisions.

## Owner/IAM

The first user receives the existing tenant `admin` role or a new tenant-owner role built from tenant permissions. It must never set `is_platform_admin`, `is_superuser`, or an elevated role slug. Username/email uniqueness policy must be made explicit because the current Django username is globally unique and the user model supports one direct tenant.

## Accounting and module initialization

- Validate module dependencies and plan inclusion before tenant creation.
- Persist `TenantModule` rows as the authoritative enablement set.
- Initialize the existing chart of accounts through `ChartService.ensure_default_chart()` and existing finance services; never build another ledger.
- Module defaults and accounting stages must be idempotent so job retry cannot duplicate records.

## Observability

Every transition logs `registration_id`, `tenant_id`, normalized subdomain, mode, stage, status, duration and safe failure category. Never log password, verification token, JWT, secret or uploaded document contents. Emit counters and latency metrics for attempts, conflicts, verification, success and failures.
